fux: a terminal multiplexer where every pane is a directory (for people, scripts and agents).
Everything is files; you need no viewer. The lines indented by four blanks are one shell session,
top to bottom: they are run as written by tools/help-agents.sh. Names here (agent-demo, job) are
examples: choose your own.

WHAT THERE IS
A pane is a directory. One small process (its holder) runs a program, as a rule on a terminal
of its own, and keeps the directory's files up to date. A workspace is a directory of panes. The
session directory holds the workspaces: $XDG_RUNTIME_DIR/fux, else ~/.cache/fux (the default
session: `fux dir` prints it). fux reads no variable of its own and gives a pane's program none.
A name always means one in the default session, wherever you type it; anything else is named
by its directory's path. A program that must know which pane it runs in is told by whoever
starts it (the path `fux start` prints), or asks the files: .here, under RESIZE, RENAME.

START A PANE
    D=$(fux dir)                              # the session directory (made when the first pane starts)
    P=$(fux start agent-demo/job -- sh)       # workspace agent-demo, pane job: prints $D/agent-demo/job
    ls "$D" "$D/agent-demo"                   # workspaces; the panes of one
NAME is WORKSPACE/PANE (or PANE alone: the workspace main, ALSO WHEN YOU TYPE IT IN A PANE OF
ANOTHER WORKSPACE). Letters, digits, . _ - only, 64 at most, no dot first, and not -, layout,
colours or keyboard; a PANE given as --out alone is the option: write main/--out for a pane of
that name. (A workspace may be a directory's path instead, one that begins with / or
. : `fux start /some/where/job` puts the pane in /some/where, a session or not, and
`fux start ./job` MAKES THE PANE'S FOLDER IN THE DIRECTORY YOU ARE IN. What is printed is the
folder's own path, links followed.) No program after -- means $SHELL, else /bin/sh. The program gets the
starter's environment and working directory, and its first size from COLUMNS and LINES (else 80, 24):
    W=$(cd / && COLUMNS=120 LINES=40 fux start agent-demo/wide -- sh -c 'pwd; exec sleep 600')
A pane is one run. A name that is there is refused ("the name is taken"), whether its pane
runs or has ended, and nothing of it is touched: rm -r its directory to start the name anew.
fux start exits 0 when the pane is up, 127 when its program is not found and 126 when it is found
and cannot be run (as a shell does: the folder stays, its log says why), 1 for any other failure.
With --out the program has no terminal: its input is /dev/null, it leads a session of its own,
and what it writes to its output and its errors goes as it is written, byte for byte, to one file
of the pane, `out`. Such a pane has `out` and none of a terminal's files (in, main/, shown, size,
cursor, modes, history, marks...): only `ctl` and the facts of its run (state, status, run, command,
generation, log). Its environment is passed on as it is, COLUMNS and LINES too. When its program
ends, its holder hangs up what is left of its group, as a terminal's end does (what should outlive
it is started with nohup or setsid, as under a terminal; what such a survivor writes still lands
in `out` after fux wait). Killed outright, its holder leaves the program running: no terminal
hangs it up. `out` is not yours to make: a file of your own of that name in a pane with a
terminal makes the viewer and .restore take it for one without.
    O=$(fux start --out agent-demo/out -- sh -c 'printf "a\377b"; echo e >&2; exit 3')
    fux wait "$O" | tail -n 1; od -c "$O/out"           # state exited 3; a 377 b e \n, nothing more

WAIT FOR WHAT YOU EXPECT
`shown/screen` is what the pane shows now, as plain text (`shown` is a link to the folder of
the screen that is drawn: under READ IT): a frame, not a log, replaced many times a
second, a few milliseconds after the program prints. So never read once and conclude, and
never sleep and hope: wait for a text, or for the frame to change, always with a limit.
    seen() { n=0; until grep -q -- "$1" "$2" 2>/dev/null; do n=$((n+1)); [ $n -lt "${3:-100}" ] || return 1; sleep 0.1; done; }
    unseen() { n=0; while grep -q -- "$1" "$2" 2>/dev/null; do n=$((n+1)); [ $n -lt "${3:-100}" ] || return 1; sleep 0.1; done; }
    frame() { cksum < "$1/shown/screen.styled"; }
    changed() { n=0; while [ "$(frame "$1")" = "$2" ]; do n=$((n+1)); [ $n -lt "${3:-100}" ] || return 1; sleep 0.1; done; }
    settled() { a=; b=x; n=0; until [ "$a" = "$b" ]; do n=$((n+1)); [ $n -lt "${2:-100}" ] || return 1; a=$b; sleep 0.3; b=$(frame "$1"); done; }
seen REGEX FILE [LIMIT] waits until the file has a matching line, unseen until it has
none. changed DIR FRAME [LIMIT] waits until the screen is another than the one you noted
BEFORE you acted; settled DIR [LIMIT] until two reads 0.3 s apart are the same. LIMIT is
in tries (0.1 s each, 0.3 for settled), 100 if not given.
EACH RETURNS NON-ZERO WHEN ITS LIMIT RAN OUT. Check it every time (`seen X FILE || exit
1`, or run your script under `set -e`): unchecked, you go on with nothing seen.
A match must be one that was not there before you acted: an old prompt, or the line you
typed yourself, matches too. So anchor (^...$), or print a tag the typed line does not
contain (below). `changed` says only that something on the screen changed: an old match may
still be there. Settled alone can be the old frame twice. A row's blanks at its end are not
in `screen` (but for a row that wraps into the next): a prompt "$ " is the line "$", and
where the cursor stands is in `cursor`. Waiting for a first prompt, for 50 tries at most:
    seen '[$#>]$' "$P/shown/screen" 50
Tries are not seconds: each also takes what it takes (more on a busy machine). For a limit
in time, compare `date +%s` in the loop, or on Linux run the wait under timeout(1).

TYPE INTO IT
`in` is a FIFO: bytes written to it are typed to the program. Enter is \r.
    f=$(frame "$P"); printf 'echo hello\r' > "$P/in"; changed "$P" "$f"; seen '^hello$' "$P/shown/screen"
    printf 'echo $((6*7))\r' > "$P/in"; seen '^42$' "$P/shown/screen"
What you typed is on the screen too (the terminal echoes it, as a rule), so the words you typed
are no evidence that a command ran. Wait for what only the program can produce: a value it
computed (42 above, which you never typed), or a whole row of its own, anchored ^ and $.
    text='any text, with % and \ in it'; printf '%s' "$text" > "$P/in"; printf '\025' > "$P/in"
Keys are their bytes: Ctrl-C \003, Ctrl-D \004, Ctrl-U \025, Escape \033, Tab \t, Backspace
\177, arrows \033[A B C D (\033OA B C D where `modes` says appcursor). One write of at most 512 bytes arrives whole; larger ones may
mix with another writer's. Paste, where `modes` says paste: \033[200~ text \033[201~.
What a program does not read: a program that reads whole lines (cat, a plain `read`) gets
at most about 4,000 bytes of one line (1,000 on macOS), the rest of the line is dropped;
under a program that reads nothing at all, typed bytes are echoed and then dropped the
same way. Only where the terminal passes keys one by one (an editor's setting) and the program
has stopped reading do they queue: the holder keeps 64 KiB, then the FIFO fills and a writer
waits. So: delivery is known only by what the program shows; send long text as lines, or as a paste.

A WRITE THAT WAITS FOR NO READER, AND WHETHER A PANE IS ALIVE
A plain write (`> "$P/in"`) waits for ever if the pane's holder was killed outright
(kill -9, a crash): the FIFOs stay with no reader, and `state` stays as it was (running). Opened
for reading and writing at once (`1<>`), a FIFO never makes the opener wait:
    [ -p "$P/in" ] && printf 'echo sent\r' 1<>"$P/in"; seen '^sent$' "$P/shown/screen"
What that gives and does not: a short write (one the FIFO has room for) cannot hang on a dead
pane, but there the bytes are lost without a word. (The `-p` test is because on a pane that ended
normally `in` is gone, and `1<>` would make a plain file of that name.) Under a program that has
stopped reading keys it can still wait, as said above. So when the answer matters, ask first whether
the pane is alive. Alive is not what `state` says: it is the holder's process, there and not a zombie:
    alive() { s=$(ps -o state= -p "$(sed -n 's/^holder //p' "$1/status")" 2>/dev/null) && case $s in ''|Z*) false ;; esac; }
    X=$(fux start agent-demo/crash -- sleep 600); kill -9 "$(sed -n 's/^holder //p' "$X/status")"   # a crash, to show it
    seen . "$X/state"; sleep 0.2; alive "$P"; alive "$X" || echo "crash is dead, though its state says $(cat "$X/state")"
    printf 'x' 1<>"$X/in"; echo "the write to the dead pane came back"
Its one limit: long after a crash the holder's number may be another process's. Exact,
where there is flock(1) (Linux): the holder holds a lock on the pane's directory while it
lives, so `flock -sn "$X" true` FAILS for a live pane and succeeds for a dead one (without
-s it also fails in the instant a `fux wait` reads a dead one).

READ IT
    cat "$P/shown/screen"                     # the screen that is drawn, one line a row
    cat "$P/shown/screen.styled"              # the same with colour codes, safe to cat
    cat "$P/main/screen"                      # the main screen (a shell's), also while vim or less covers it
    cat "$P/history"                          # lines that scrolled off the top (history.1: older)
    cat "$P/history.styled"                   # the same lines with colour codes (history.styled.1: older)
    cat "$P/size" "$P/cursor" "$P/modes" "$P/state" "$P/status"
One fact, one small file (absent until there is something to say, where noted):
size    COLS ROWS, e.g. `80 24`
cursor  ROW COL shown|hidden SHAPE, from 0, of the screen that is drawn: `2 8 shown 0` is
        row 2, line 3 of `shown/screen`
        (a fifth word, `#rrggbb`, if the program gave the cursor a colour; a colour a program
        sets for its pane is in `shown/screen.styled` as direct colour: `38;2;R;G;B`, `48;2;R;G;B`
        on every cell of the default background, `58:2::R:G:B` for an underline)
modes   words, or an empty line: appcursor, keypad, paste, focus, mousesgr, mouseN, keysN
state   running | hungup | exited CODE | killed SIGNAL (lost ERROR: the holder could not wait)
run     32 hex digits: which run this folder is, written once. A name removed and started anew
        has another: keep it (`read -r run < "$P/run"`) to know later that $P is still that pane
status  three lines: holder N / pid N (the program's) / command ... (no pid line until the
        program runs: none at all if it could not be started)
command the program and its arguments as given, each ended by a zero byte (absent until the
        program runs): tr '\0' '\n' < command
main/, alt/, shown   a folder for each screen, the same five names in each (screen,
        screen.styled, lines, links, pictures), in a pane with a terminal: main always, the
        screen a shell prints on; alt while a full-screen program has the alternate screen (kept
        if the pane ends under it); shown, a link to the one that is drawn. A name never changes
        which screen it means
lines   (in a screen's folder) two lines: how many lines are before the screen's first row
        (in main: of all the lines the pane printed, so the number, from 0, of that row's line;
        in alt: 0, as that screen is in no text); then the screen rows (from 0) that continue
        the row above, `1 2` being one line in 3 rows (empty if none; 0 in main: row 0
        continues history's last line). `{ read -r top; read -r wraps; } < main/lines`
generation   a number: odd while the holder is writing the pane's files, even when they
        agree (below)
title   the window title the program set (absent until it does)
cwd     the program's directory, if it announces it (absent else): a shell must, at each
        prompt, a % in the path as %25. For bash: PROMPT_COMMAND='printf "\033]7;file://%s\007" "${PWD//%/%25}"'
notice  `N WORDS`: N grows with each writing of the files that had a notice, WORDS may be
        none (a bell). E.g.
        `1 the build is done`. Absent until the first.
marks   `LINE AT KIND`, a line for each prompt mark of a shell that makes them (below): the
        last thousand
marks.dropped   a number: how many marks were dropped from the front of `marks` (`0` until
        there were more than a thousand). Line n of `marks` is mark number that + n (below)
links   (in a screen's folder) `LINE COL LEN ADDRESS` for each link (OSC 8) on that screen,
        e.g. `24 0 4 https://x.y`: LINE counts as the first line of that folder's `lines`
        does (screen row = LINE - that number, if no row above wraps), COL is the first cell
        from 0, LEN the number of cells
out     (a pane started with --out, and only such a pane: it is made before `run`) what its
        program wrote to its output and errors, as it wrote it, without bound
log     what the holder refused or lost. (Also: clipboard; and in a screen's folder `pictures`,
        a line `pic-N.sixel ROW COL COLS ROWS CELL-WIDTH CELL-HEIGHT` for each picture on that
        screen, the file being in the pane's folder.)
One file read by itself is always whole. Two files read one after the other may be of two
writings of the files (a `lines` one scroll behind its `screen`). Where they must agree,
read `generation`, the files, and `generation` again, and keep what you read only if both
times it was the same even number; else read again, with a limit:
    together() { d=$1; shift; tries=0; until g=$(cat "$d/generation") && [ $((g % 2)) -eq 0 ] && "$@" && [ "$g" = "$(cat "$d/generation")" ]; do tries=$((tries+1)); [ $tries -lt 100 ] || return 1; sleep 0.05; done; }
    first() { top=$(sed -n 1p "$P/main/lines") && row=$(sed -n 1p "$P/main/screen"); }
    together "$P" first && echo "the main screen's first row is line $top of the pane's text: $row"
(It runs the command after DIR until the read is one to keep, so the command starts anew
each time: one that writes a file writes it anew, `> file` inside it and not after `together`.
It keeps what it knows in `d`, `g` and `tries`: the command must leave those names alone, and
not call `together` itself. DIR must name the same pane throughout. The number speaks for what
the holder alone writes: not for `cwd` (the program's to write too), `out` (the program's
alone), `log`, the FIFOs or files of your own. A pane whose holder was killed
while it wrote stays odd: the limit runs out, and you take the files as they are.)
The text a pane with a terminal keeps, oldest first, wrapped rows joined into lines (of one
started with --out it is `cat "$O/out"`):
    whole() { cat "$1/history.1" "$1/history" 2>/dev/null || :; awk -v w="$(sed -n 2p "$1/main/lines")" 'BEGIN { n = split(w, a, " "); for (i = 1; i <= n; i++) j[a[i] + 1] = 1 } { r[NR] = $0; if ($0 != "") last = NR } END { for (i = 1; i <= last; i++) printf "%s%s", (i > 1 && !j[i] ? "\n" : ""), r[i]; if (last) print "" }' "$1/main/screen"; }
    whole "$P" | tail -n 5
    f=$(mktemp); snap() { whole "$P" > "$f"; }; together "$P" snap && tail -n 1 "$f"; rm -f "$f"
It is exact for a pane that is still or ended, whichever screen it shows, and under `together`
(the line above) for one that prints meanwhile, but for: colours, blanks at a line's end,
empty lines at the very end, what was erased or written over, and text older than the two
history files keep (4 MiB or more; a line of over 8 MiB that never ends is ended there: the
text has a line end the program did not print, and `log` says so).

RUN A COMMAND, GET ITS OUTPUT AND EXIT CODE
Surest: make the command the pane's program. `fux wait DIR` returns when the pane's holder
is gone, and prints `pid N` and `state ...` as the files have them: the exit code is in that
line (fux wait itself exits 0). A holder whose program ended wrote `state`, and for a pane with a
terminal its last screen, first; one that was killed did not, and `state running` is what you
get. The pane stays.
    J=$(fux start agent-demo/ls -- sh -c 'ls /; exit 3')
    code=$(fux wait "$J" | sed -n 's/^state exited //p'); echo "exit code $code"
    whole "$J"                                # all it printed (cat "$J/out", started with --out)
fux wait has no limit: it waits as long as the program runs. To bound it, wait for the
holder to go, with a limit, and then ask:
    ended() { n=0; while alive "$1"; do n=$((n+1)); [ $n -lt "${2:-100}" ] || return 1; sleep 0.1; done; }
    ended "$J" 50 && fux wait "$J" | tail -n 1
In a shell you keep typing into, print a tag after the command that the typed line itself
does not contain (here the typed line has $? where the output has a number):
    printf 'ls /nonexistent; echo "<<t1:$?>>"\r' > "$P/in"; seen '<<t1:[0-9]*>>' "$P/shown/screen"
    grep -o '<<t1:[0-9]*>>' "$P/shown/screen"       # <<t1:2>> : the exit code (use a new tag each time)
A shell that marks its prompts (OSC 133) needs no tag: each mark is a line `LINE AT KIND`
in `marks`. This bash makes three kinds: `prompt`, `command` (where typing starts) and
`end CODE` (written before each prompt, the first one too: `end 0` is there from the
start). The fourth, `output`, needs PS0='\e]133;C\a' and bash 4.4.
    S=$(fux start agent-demo/marked -- env PS1='\[\e]133;A\a\]$ \[\e]133;B\a\]' PROMPT_COMMAND='printf "\e]133;D;%s\a\e]7;file://%s\a" "$?" "${PWD//%/%25}"' bash --norc -i)
So never wait for "an end": wait for a NEWER one than there was before you typed. Neither the
file's count nor a mark's place says that (`marks` keeps the last thousand, and a mark moves
with its text: a clear, a line inserted). Its number does: line n of `marks`, from 1, is mark
number `marks.dropped` + n, for as long as it is listed. `last` prints the number of the last
mark of a kind (with none listed, of the last mark dropped): an `end`'s never goes back.
    last() { awk -v kind="$2" 'NR == 1 { n = $1; last = n; next } $3 == kind { last = n + NR - 1 } END { print last }' "$1/marks.dropped" "$1/marks"; }
    more() { n=0; while [ "$(last "$1" "$2")" -le "$3" ]; do n=$((n+1)); [ $n -lt "${4:-100}" ] || return 1; sleep 0.1; done; }
    look() { e=$(last "$S" end) && p=$(last "$S" prompt); }
    seen ' prompt$' "$S/marks"; together "$S" look
    printf 'cd /; false\r' > "$S/in"; more "$S" end "$e"; more "$S" prompt "$p"       # its end, then the next prompt
(The `end`s numbered above $e are the commands that ended since, each once. If `marks.dropped`
is by then above the number of the last mark read before, over a thousand marks came between
the two looks: that many came and went unread. `more` reads the two files as they are: read
between two writings its number is too small, never too big, and it looks again.)
    grep ' end' "$S/marks" | tail -n 1; cat "$S/cwd"       # LINE AT end 1, and /

FULL-SCREEN PROGRAMS (vim, less, htop)
While one has the alternate screen, there is `alt/` with the program's own screen, `shown`
leads there, and `main/screen` is still what the shell showed before it opened, read without
leaving it. `alt/` is filled before `shown` is turned to it, and removed after it is turned
back: wait for the link, not for a file. Send keys as bytes; after each, wait for a changed
frame or for the text you expect.
    shows() { n=0; until [ "$(readlink "$1/shown")" = "$2" ]; do n=$((n+1)); [ $n -lt "${3:-100}" ] || return 1; sleep 0.1; done; }
    printf 'less "%s/status"\r' "$P" > "$P/in"; shows "$P" alt; readlink "$P/shown"; ls "$P/alt"     # alt, and its five files
    grep '<<t1' "$P/main/screen"              # under less: the shell's screen, with the tag printed above
    f=$(frame "$P"); printf '/pid\r' > "$P/in"; changed "$P" "$f"      # search; vim: printf '\033:wq\r'
    printf 'q' > "$P/in"; shows "$P" main; readlink "$P/shown"                                    # main
A program that asks what its terminal is gets fux's own answers: XTVERSION `fux N`;
COLORTERM=truecolor in its environment; and by name (XTGETTCAP) these, any other being "not
valid": TN name Co colors RGB Tc setrgbf setrgbb Smulx Setulc Ss Se. So Neovim uses true
colour and curly underlines with no setting.

RESIZE, RENAME, RING, END
`ctl` is a FIFO too, one command a line: resize COLS ROWS [CELL-WIDTH CELL-HEIGHT] (a cell's
size in pixels), notify WORDS, kill.
    echo 'resize 100 30' > "$P/ctl"; seen '^100 30$' "$P/size"
    printf 'notify %s\n' 'the build is done' > "$P/ctl"; seen 'build is done' "$P/notice"
    mv "$W" "$D/agent-demo/broad"; W=$D/agent-demo/broad    # a rename: the pane lives on, under the new path
    echo kill > "$P/ctl"; fux wait "$P"       # hangs up the program: state killed 1, or exited N
A renamed pane is a tab of its own in the layout again. Move only within one filesystem.
(To keep its place in the layout, a script that comes with a viewer's keys renames under the
layout's lock: .rename WORKSPACE-DIRECTORY OLD NEW. And .here [SESSION-DIRECTORY], beside
it, prints the directory of the pane it is run in: it must be given the session's directory
wherever that is not the default one, as nothing in a pane says which session it is in. Both
need more than sh: the optional section below says what.)
`kill` hangs up (SIGHUP), as closing a terminal does. It does not remove the pane: the
directory stays, with the last screen and state. It does not force: a program that
ignores it lives on, with `state` hungup, and is typed to no more; then signal the program (never the holder):
    T=$(fux start agent-demo/stubborn -- sh -c 'trap "" HUP; echo ready; sleep 600; echo over')
    seen ready "$T/shown/screen"; echo kill > "$T/ctl"; seen hungup "$T/state"
    p=$(sed -n 's/^pid //p' "$T/status"); kill -TERM "$p"; fux wait "$T"    # state killed 15
`state` and `fux wait` are about the pane's program alone, not about what it started:
here the shell is gone and its `sleep` runs on. The program leads a process group of its
own number, and what it started is in it as a rule (a job-control shell's jobs are not):
    kill -0 -"$p" && echo "something of pane stubborn still runs"       # pgrep -g "$p" lists it
    kill -TERM -"$p"; sleep 0.3; kill -0 -"$p" 2>/dev/null || echo "nothing of it is left"
Removing a pane's directory ends the pane too (its holder sees it within 2 seconds).
In a pane with no terminal (--out) `ctl` has one command, kill [SIGNAL]: its holder, the program's
parent, sends the program's process group the signal (1, the hangup, if none is named), until
it has seen the program end, and reaps the program only after that: the number is the group's
throughout, and no number read from a file is signalled. Removing the folder is that
hangup too, and so is the program's end.
Ended with SIGTERM:
    K=$(fux start --out agent-demo/sleeper -- sleep 600); echo 'kill 15' > "$K/ctl"; fux wait "$K" | tail -n 1

MANY PANES
    for i in 1 2 3; do fux start "agent-demo/w$i" -- sh -c "sleep 0.$i; echo done $i; exit $i" > /dev/null; done
    for i in 1 2 3; do fux wait "$D/agent-demo/w$i" | tail -n 1; done
Every workspace and pane of the session, with its state and command:
    for q in "$D"/*/*/; do [ ! -f "$q/state" ] || echo "${q#"$D"/} $(cat "$q/state") : $(sed -n 's/^command //p' "$q/status")"; done

WHAT A PERSON SEES
`fux view WORKSPACE` draws a workspace in a terminal (C-b d leaves it). Panes run the same
without it. Left alone it draws only the panes of the tab shown, with lines between them:
no bar, no tab names. Those are on its last row only after the prefix C-b (\002), while
its menu is open; Escape closes them. It shows each pane as a tab unless the workspace's
`layout` file says otherwise; edit that with `fux layout WORKSPACE EDIT`: the workspace first,
always, by its name or its directory (`fux layout` with nothing after it prints the layout of
main, wherever it is typed). Two panes above and one below, across:
    fux layout agent-demo split col w2 beside ls    # w2 below ls: do this one first
    fux layout agent-demo split row w1 beside ls    # w1 to the right of ls, above w2
    fux layout agent-demo pane ls                   # ls gets the keys
    fux layout agent-demo                           # print it: * marks the tab shown
Edits: split row|col PANE [beside PANE] · pane PANE · focus left|right|up|down|next|prev ·
tab next|prev|- (and break, swap, size, rotate, arrange).
To see what a person would, run the viewer in a pane of ANOTHER workspace and read it:
    V=$(COLUMNS=100 LINES=30 fux start agent-view/v -- fux view agent-demo); seen '│' "$V/shown/screen"
    printf 'notify %s\n' 'look here' > "$W/ctl"; seen ' broad: look here$' "$V/notice"
    printf '\002' > "$V/in"; seen ' agent-demo .* broad' "$V/shown/screen"       # the bar: workspace, tabs
    printf '\033' > "$V/in"; unseen ' agent-demo ' "$V/shown/screen"            # (a key right after Escape would join it)
    cat "$V/shown/screen"; printf '\002d' > "$V/in"; fux wait "$V"       # C-b d: the viewer leaves
A viewer sets the size of the panes it shows to their tiles. A notice (`notify`, a bell)
of a pane in the workspace shown, made after it first looked, goes to the viewer's terminal as `PANE: WORDS`,
and its tab is marked; a viewer in a pane has that in its own pane's `notice`, as above
(`N broad: look here`; a bell is passed on as a bell, so there it is the number alone).
From inside a pane, to the pane's own ctl: its directory is what whoever started the program
told it, or what .here prints: printf 'notify %s\n' done > "$(sh ~/.config/fux/keys/.here)/ctl".
A viewer writes in the session `keyboard` and, only if its terminal answered, `colours`
(what its terminal can do; harmless, left behind), its key scripts in $XDG_CONFIG_HOME/fux/keys,
else ~/.config/fux/keys (or the directory named: fux view WORKSPACE KEYS), and while it runs a folder

IF YOU HAVE PERL (optional: nothing else on this page needs it)
The sh forms above can lose a write to a dead pane without a word, wait under a program that
stopped reading, and take a long-dead pane for alive. With perl (Linux and macOS ship it) there are surer
forms. A write that never waits and fails at once, saying why (512 bytes at most: of more, a part may go):
    send() { perl -e 'use Fcntl; -p $ARGV[0] or die "$ARGV[0]: not a FIFO\n"; sysopen(F, $ARGV[0], O_WRONLY|O_NONBLOCK) or die "$ARGV[0]: $!\n"; local $/; defined syswrite(F, <STDIN>) or die "$ARGV[0]: $!\n"' "$1"; }
    printf 'x' | send "$W/in"; printf 'x' | send "$X/in" || echo "refused at once"
"not a FIFO", "No such file": the pane ended or is gone; "No such device or address": no
holder reads, it is dead; "Resource temporarily unavailable": alive, its queue full. And
alive by the lock the holder holds on the pane's directory, which no pid can fake (the keys'
.here and .rename, named under RESIZE, RENAME, are perl for that lock, and are not there without it):
    locked() { perl -e 'use Fcntl ":flock"; open(D, "<", $ARGV[0]) or exit 1; exit(flock(D, LOCK_SH|LOCK_NB) ? 1 : 0)' "$1"; }
    locked "$W"; locked "$X" || echo "crash holds no lock"
In python: os.open(path, os.O_WRONLY | os.O_NONBLOCK) then os.write, and fcntl.flock.

MANNERS AND CLEANING UP
Work in workspaces of your own (agent-TASK). Never type into, resize, kill, rearrange or
remove a pane you did not start, nor edit another workspace's layout. Before you remove,
look at what it is (`status` names the command). When done, remove what you started and
nothing else; removing a workspace ends every pane in it:
    cat "$D"/agent-demo/*/status | grep '^command'
    rm -r "$D/agent-demo" "$D/agent-view"
A session holds nothing else but the viewer's files named above (and, where a person's key
script was cut short, a dot-named file or folder of its own). In a container with no
init, ended holders stay as zombies (dead, holding nothing): use docker --init.
