# Rewrite fux and zor from scratch as ECS-native Bevy applications

Decision record and execution prompt, 2026-09-15. Decisions taken by the user in this session: two applications in two crates (fux and zor), the rewrite lives on an orphan branch of this repository, every wire protocol is replaced (BRP JSON-RPC over `RemoteHttpPlugin` for control, a new attachment stream), `local-ipc` is dropped entirely, Bevy's own runtime crates replace tokio/tracing wherever a Bevy crate exists, and this document precedes code. The guiding rule is: **if Bevy has a mechanism for it, use Bevy's mechanism**; the only permitted exceptions are listed in section 2.

This is a reimagining, not a port. The old fux modelled a multiplexer the way tmux does: a binary split tree per tab, a fixed workspace/tab/pane hierarchy, a hand-written layout algorithm, hand-written chrome and a bespoke protocol for each. None of those concepts is a requirement. The requirements are the *behaviours* users and zor depend on (persistent processes, exact-process attachment, receipts, retained evidence, multi-viewer correctness, bounded resources) and the principle that the session **is** a `bevy_ui` scene: any `Node` tree taffy can lay out is a valid layout, a pane is a leaf with a terminal in it, chrome is nodes, a saved layout is a scene, a template is `bsn!`, an edit is a hierarchy or style edit, and the client is a painter of `ComputedNode`s. Where the old product had a concept that `bevy_ui`, `bevy_scene`, `bevy_picking`, `bevy_input_focus`, `bevy_state` or `bevy_asset` already provide, the Bevy concept replaces it outright; the old concept is not re-created on top. The same rule is applied to zor: its dashboards and plugin panes are scenes fux hosts, not a second TUI.

Implement this work completely. Do not stop at a scaffold, a design revision or a subset of the entity graph. The result is a runnable fux and zor whose authoritative state is a `bevy_ecs` World in a `bevy_app::App`, whose public control surface is the Bevy Remote Protocol served by `RemoteHttpPlugin` on loopback with capability tokens, whose layouts and templates are `bevy_ui` scenes, whose persistence is reflection-based world serialization over an allowlisted projection, and whose invariants are at least those of the current implementation. Backward compatibility is not a goal; user data, live sessions and the fux/zor/koh ownership boundaries are.

## 3. fux design

### 3.1 Application shell

`fux serve` builds an `App` with a custom runner (`examples/app/custom_loop.rs` pattern) that owns no reactor of its own: PTY readers, the BRP HTTP acceptor (`bevy_remote::http`, which already runs on `IoTaskPool`) and the attachment listener are `IoTaskPool` tasks that push typed messages into `async_channel`s held as resources; asset file watching is `bevy_asset`'s own `notify` thread. The runner blocks on those channels plus the World's next deadline, feeds a bounded batch, calls `app.update()` once, then drains `Effect` messages to the adapters. `app.finish()`/`app.cleanup()` run once before the loop. Idle means no wake-ups: `bevy_time`'s `Time`/`Timer` values are advanced from the runner clock and only read inside a step; the runner, not a schedule, sleeps until the next `Timer` deadline the World reports. Preserve today's stream coalescing (3 ms gap / 1 ms wait) and per-source budgets as runner parameters.

Schedules: use `bevy_app`'s `Main` with `First → PreUpdate → Update → PostUpdate → Last` mapped to `Ingest → Requests/Completions → Lifecycle/Layout → Projection → Effects`. `RemotePlugin` inserts `RemoteLast` after `Last`; fux moves it with `MainScheduleOrder::insert_after(First, RemoteLast)` so BRP mutations land before the `Requests` phase and are visible in the same update's frames, instead of one update late. Every phase boundary applies deferred commands; no system relies on ambiguous ordering. `AssetEventSystems` runs in `PostUpdate`, so systems reacting to `AssetChanged<T>` are ordered after it (or run the next update). Server-wide modes (`Starting`, `Serving`, `ShuttingDown`) are `bevy_state` `States` with `OnEnter`/`OnExit` schedules and `in_state` run conditions, never boolean mode flags; `StateTransition` runs at the start of `Main`, so a `NextState` written during an update is applied on the *next* update and the runner schedules one more update after any step that wrote `NextState` instead of sleeping. Keep an invariant-checking system in `Last` in debug/test builds that asserts the whole of section 3.5.

Signals and shutdown: `SIGINT`/`SIGTERM` are delivered to the runner (a signal handler writing to an `async_channel`, never a Bevy system), which writes `NextState(ShuttingDown)`; `OnEnter(ShuttingDown)` emits `Terminate` for every live pane (SIGHUP to the process group, SIGKILL after one second, as today), the runner keeps stepping until no pane is live or a five-second deadline passes, then returns `AppExit`. `SIGHUP` on the server is ignored; panes get theirs through `Terminate`. The runner never busy-polls signals: a hot pane must not delay signal delivery, so the signal channel is one of the sources the runner blocks on with priority.

### 3.2 Entity graph and components

Entities: `Server` (one), `Workspace`, layout **template** nodes (an inert `Node` subgraph per root, never laid out), layout **instance** nodes (one clone of a template root per viewer showing it, laid out against that viewer's camera), `Pane` (the shared process entity: `Terminal`, PTY identity, receipts), `Surface` (a template leaf whose subtree is a scene streamed by another app, section 3.13), `Viewer` (with its `Camera`), `ControlClient`, `InputOperation`, `FinalRecord`, plus observer entities for the reactions listed in 3.3. There is no `Tab` entity kind: a "tab" is a template root under a workspace and the tab strip is a projection of those roots. Terminal rows and cells are never entities. Diagnostics use `bevy_log` (`LogPlugin` alone writes to stderr; fux supplies a `custom_layer` built on `bevy_log::tracing_subscriber` that writes the daemon log file, never the terminal) and `bevy_diagnostic` (`EntityCountDiagnosticsPlugin`, step time, and custom `Diagnostic`s for PTY bytes/s, frames/s, wake-ups/s, published through `world.get_resources`).

Relationships (source of truth; reverse side is an index, never edited directly):

| Relationship | Reverse | Notes |
|---|---|---|
| `RootOf(workspace)` | `Roots` | every template root (tab) belongs to one workspace; `RootOrder(Vec<Entity>)` on the workspace is the user-visible order, validated against `Roots` |
| `ChildOf(parent)` | `Children` | Bevy's hierarchy **is** the layout, in both the template subgraph and each instance subgraph. `linked_spawn = true`; template leaves and instance leaves never carry the `Terminal`, so cascading despawn of a tree can never kill a process |
| `InstanceOf(template_node)` | `Instances` | each instance node points at the template node it was cloned from; re-cloning a subtree after an edit despawns the old instances and re-links |
| `Shows(pane)` | `ShownBy` | from an instance leaf to the shared pane entity; the pane's emulator size is the minimum over its `ShownBy` instances' `ComputedNode` content sizes |
| `Places(pane)` | `PlacedIn` | from a template leaf to the pane it places; exactly one template leaf per pane per workspace; moving a pane is a template `ChildOf` edit |
| `PaneIn(workspace)` | `WorkspacePanes` | ownership for authority checks |
| `Viewing(workspace)` | `ViewedBy` | viewer attachment; `Showing(template_root)` is a plain component on the viewer |
| `Targets(pane)` | `TargetedBy` | where a viewer's bytes go (`examples/ecs/relationships.rs` `Targeting`/`TargetedBy`). This is the server's whole notion of "focus": presentation focus lives in the viewer App (3.11). An exact attachment is a `Targets` that cannot be retargeted |
| `OperationOn(pane)` | `PaneOperations` | input receipts; `linked_spawn = true` is acceptable here because a receipt cannot outlive its pane |

Components, split by mutation owner (one system set writes each):

- Immutable identity (`#[component(immutable)]`, hook-indexed into `Ids`): `PaneId`, `NodeId` (public id for any addressable node), `ViewerId`, `WorkspaceName`, `WorkspaceStream`, `LaunchAttribution { workspace_name, stream, argv, cwd }`. `Name` from `bevy_ecs` carries user-facing labels so inspectors and the tab strip show them.
- Process: `Process` enum `Starting | Live{pid} | Eof{pid} | Terminating{pid, since} | Exited{code}`; `FinalRetention(ms)`.
- Terminal: `Terminal` (emulator + history; owns its own damage/sequence), `Title`, `RightClickPolicy`, `OutputPacing { last_event_ms, last_event_seq }`.
- Layout and appearance (all `bevy_ui` types, all reflected, all editable through the scene API of 3.9): `Node` (flex, grid, absolute positioning, `min_width`/`min_height`, `overflow`, `border`), `ZIndex`/`GlobalZIndex`, `BackgroundColor`, `BorderColor` on template nodes and copied to instances; `ComputedNode` (read-only geometry in cells), `UiTargetCamera`, `ScrollPosition`, `Zoomed(Entity)` and per-viewer `Display` overrides on instance nodes only; `LayoutGeneration(u64)` on template roots.
- Viewer: `Viewport { rows, cols }`, `Camera` + `RenderTarget::None { size }` (the layout target for this viewer's instances, section 3.4), `Showing(template_root)`, `RequestQueue`, `CreationBarrier(Option<Entity>)`, `ProjectionBaseline { scene revision; per pane: seq, size }`, `Notice` with a `bevy_time` `Timer`, `Detaching`. No focus component: input routing is the `Targets` relationship, and focus history is viewer-local.
- Presence instead of flags: `Disabled` (default query filter) on `Starting` panes and `Retiring` workspaces, so ordinary queries never see them. **Never on any entity that has a `Node`**: `bevy_ui`'s own queries are default-filtered, so a `Disabled` node vanishes from layout and stops `ComputedUiRenderTargetInfo` propagation to its subtree. Template nodes are not laid out because they carry no `UiTargetCamera` and no viewer camera resolves as default (no `IsDefaultUiCamera` exists), not because they are disabled. `Open`, `Retiring { since_ms }`, `Creation { requesters, kind }` remain as markers where a transition needs data.

`Changed<T>` is used for local invalidation only: projection on `Changed<Terminal>`/`Changed<Title>`/`Changed<ComputedNode>`/`Changed<Node>`. Semantic revisions that cross the wire (`Terminal` sequence, `LayoutGeneration`, scene revision, event cursors) remain explicit integers. Use `set_if_neq` for every derived write.

### 3.3 Hooks, observers and events policy

Hooks: only index maintenance (`Ids` maps on insert/discard of immutable ids, workspace-name uniqueness). Hooks never spawn processes, emit effects or decide policy. Uniqueness is validated at the typed transition before insertion; the hook only records.

Every lifecycle fact is an `EntityEvent` with `#[entity_event(propagate)]` (bubbles up `ChildOf`; `examples/ecs/observer_propagation.rs`) that also derives `Reflect` with `#[reflect(Event)]` and is `register_type`d, which is what `world.observe+watch` requires: `PaneSpawned`, `PaneOutput { seq }`, `PaneTitleChanged`, `PaneExited { code }`, `PaneClosed`, `TabEmptied`, `WorkspaceRetired`, `ViewerAttached/Detached`, `Bell`. Their reflected fields carry ids and counters, never terminal content, because `observe+watch` serializes the whole event body. They are *triggered by* the ordered lifecycle systems after a transition commits; they never *decide* a transition. Consumers are observers: the retained event log (feeds `fux/events+watch` and `world.observe+watch`), the `bevy_audio` bell (feature `bell`), diagnostics counters, zor's watcher, and viewer-local reactions. Observers may queue commands and write messages; they may not touch OS handles or apply layout edits. Authority checks and persistence stay in systems.

Pointer interaction uses `bevy_picking` (section 3.4): `On<Pointer<Press|Release|Drag|DragEnd|Click>>` observers on nodes (pane content and pane borders) are the *only* place mouse policy lives. Interaction state uses `bevy_ui`'s own marker components (`Pressed`, `InteractionDisabled`, `Selected`; `crates/bevy_ui/src/interaction_states.rs`), never booleans. `bevy_picking`'s `Hovered`/`DirectlyHovered` components are hard-wired to `PointerId::Mouse` and are meaningless for per-viewer `PointerId::Custom` pointers; hover state on the server is read from `HoverMap` per pointer. Observers that a template must attach at spawn use a bundle-effect helper equivalent to `bevy_ui_widgets::observe` (~80 lines, `unsafe`, copied with attribution or reimplemented), not a follow-up `commands.entity(e).observe(..)` that can race the spawn. `Pointer<Click>` is only generated after a matching `Press` on the same entity, so fixtures drive press/release pairs, never synthetic clicks.

### 3.4 Layout is `bevy_ui`, and only `bevy_ui`

A workspace's layout is a set of template roots. Each root is any `Node` tree: flex rows and columns nested to taste, `Display::Grid` with `grid_template_columns/rows` for dashboards, `PositionType::Absolute` children for floating or overlay panes, `Overflow::scroll` containers with `ScrollPosition` for long lists, `min_width`/`min_height` for terminal minimums, `border` for pane frames, `ZIndex` for stacking. A pane leaf is a `Node` that `Places` a pane; a container is a `Node` with children; nothing else is special. The old two-child split with a ratio is one composition the default templates happen to use (`Node { flex_direction: Row } [ pane { flex_grow: 1.0 }, pane { flex_grow: 1.0 } ]`); it is not a type, a constraint or an API. Separators are not entities: pane frames are `Node.border` and `BorderColor`, painted by the viewer from `ComputedNode.border`.

**Instances, not shared roots.** Bevy never lays one UI tree out against several cameras; multi-window and split-screen apps spawn one tree per camera and share the data behind them. fux does the same: when a viewer shows a root, fux clones that template root with `EntityCloner` (`linked_cloning`) into an **instance** under the viewer's camera (`UiTargetCamera(viewer_camera)` on the instance root, `InstanceOf` on every node, `Shows(pane)` on every leaf), so every laid-out root has exactly one camera by construction and no camera is ever chosen. Viewer-local layout state lives on instance nodes — `ScrollPosition`, zoom (`Zoomed` + `Display::None` off the zoomed path), transient `Display` overrides — and is keyed by `NodeId` so it survives re-cloning. Per-viewer zoom and per-viewer scroll are therefore free, and the multi-client behaviour matches Herdr 0.9 ("different tabs fit their viewing clients"). Edits (`node.*`, 3.9) apply to the **template**; the touched subtree's instances are despawned and re-cloned in the same update, viewer-local state re-applied, `LayoutGeneration` bumped. At terminal scale (tens of nodes, a handful of viewers) this is cheaper than the old shared-layout bookkeeping, and it is the same mechanism scene reloads use.

**The layout viewport is a camera, not a window**: `ui_layout_system` sizes each root from `ComputedUiRenderTargetInfo`, which `propagate_ui_target_cameras` derives from the root's `UiTargetCamera` (`crates/bevy_ui/src/update.rs:115-172`), and in this tree only `bevy_render::camera_system` writes `Camera::computed.target_info` — which is excluded. So every viewer owns a `Camera` entity with `RenderTarget::None { size: UVec2::new(cols, rows) }` and a fux system writes `camera.computed.target_info = Some(RenderTargetInfo { physical_size: (cols, rows), scale_factor: 1.0 })` on attach and resize (`Camera.computed` and `RenderTargetInfo` are public); `UiScale` stays 1.0 and cameras have no `Viewport`. With that, `ComputedNode` is in cells and geometry is never computed by fux code: the `Layout` phase runs `UiSystems::Layout` (`UiPlugin` chains `Prepare → Propagate → Content → Layout → PostLayout` in `PostUpdate`), then a `PostLayout` system takes, for each pane, the minimum content size over its `ShownBy` instances' `ComputedNode`s, resizes the emulator and emits `ResizePty` only on change. "Lay out against the smallest viewer" is a relationship fold, not a rule. A pane nobody shows keeps its last size.

Mutations are template edits, validated before commit and rejected on a stale `LayoutGeneration`: spawn a node (with an optional `PaneTemplate` to launch a terminal it will place), despawn a node (never one that `Places` a live pane; the pane is closed through its own lifecycle first), reparent, reorder among siblings, patch `Node`/`ZIndex`/`BackgroundColor`/`BorderColor` fields, move a root between workspaces. Instance-only edits (`scroll`, `zoom`, `unzoom`, transient `display`) are addressed by viewer and node and never touch the template. Validation: depth ≤ 64, nodes per workspace ≤ configured limit, a placing leaf has no children, every target inside the caller's workspace grant, every pane placed by exactly one leaf. Convenience operations (`split`, `swap`, `close`) are templates over those primitives and live in the CLI and viewer, not in the server.

Mouse: `bevy_picking`'s `PickingPlugin` + `InteractionPlugin` with a fux backend (the `bevy_ui` `picking_backend` is feature-gated off and needs a `PrimaryWindow`; reuse its geometry only: `ComputedNode::contains_point`, `UiGlobalTransform`, `UiStack` order, `clip_check_recursive`, `crates/bevy_ui/src/picking_backend.rs:150-200`). The viewer adapter writes `PointerInput` messages for one `PointerId::Custom` per viewer with `Location { target: NormalizedRenderTarget::None { width: cols, height: rows }, position: cell }` (built with `RenderTarget::None { size: UVec2 }.normalize(None)`); the backend only considers instance nodes under that viewer's camera and emits `PointerHits` whose `HitData.camera` is that camera and whose `HitData.extra` names the hit region (`Content` or `Border(side)`, from `ComputedNode.border`). Retarget on press (`Targets` ← the leaf's `Shows`), border drag-to-resize (`Pointer<Drag>` on a border region patches, on the **template**, the sibling `flex_grow`/`flex_basis` or `grid_template_*` track it belongs to), pane drag-to-move (template reparent on `DragDrop`), wheel-to-history or wheel-to-`ScrollPosition` on the instance for scroll containers, and right-click policy are observers on the picked instance entities that resolve `InstanceOf` to act. Applications that request mouse reporting receive translated events instead; the choice is a component on the pane (`RightClickPolicy`, `MouseMode` mirrored from the emulator).

Scenes: a workspace's layout is exported as a `DynamicWorld` of the allowlisted **template** subgraph (`Node`, `ChildOf`/`Children` order, `ZIndex`, `BackgroundColor`, `BorderColor`, `Name`, `PaneId` on placing leaves, `RootOrder`) via `DynamicWorldBuilder::deny_all()` + explicit allows, serialized as RON; applying one validates the document against an inert World, resolves `PaneId → Entity`, checks the expected `LayoutGeneration`, then commits into the template with `EntityCloner` and re-instances. A plain scene never launches processes; a *template scene* (leaves carrying `PaneTemplate`) may, through the same `Requests` phase as any spawn. Users write layouts as scene assets in the config directory and select them by name; `bsn!` provides the built-in ones.

### 3.5 Invariants (must hold after every `update`)

Every pane has exactly one `PaneIn` and exactly one `PlacedIn` template leaf, or is `Disabled` (`Starting`, or closing); a template leaf that `Places` has no `Children`; every template root has `RootOf` and appears exactly once in its workspace's `RootOrder`; template nodes have no `UiTargetCamera`; every instance node has `InstanceOf` to a live template node of the same shape, every instance root has `UiTargetCamera` naming its viewer's camera, and a viewer has at most one instance per template root it `Shows`; every instance leaf `Shows` the pane its template leaf `Places`; a viewer's `Targets` pane is placed in a root that viewer shows, unless the attachment is exact; `Ids` maps equal the set of live immutable id components; no `Disabled` entity and no `Display::None` subtree contributes to a projected frame; a `Retiring` workspace admits no new attachments or requests; effect queues are empty after the runner applies them; a pane's `Process` pid never changes except `Starting → Live`; `Children` order equals the projected order; depth and node counts are within limits.

### 3.6 OS adapters and effects

Unchanged in principle: the World never holds an OS handle. `Effect` messages (`SpawnPane`, `WritePty`, `ResizePty`, `Terminate`, `SendFrame`, `PublishEvent`) are drained by the runner and applied by the adapter, which converts OS activity into `Inbound` messages; BRP replies travel back through `bevy_remote`'s own `BrpMessage.sender`, not through effects. Bevy `Messages` are used only within one `update`; the runner writes the batch and the final system clears it. Durable queues (receipts, final records, retained events) are components/resources with explicit bounds.

### 3.7 BSN templates

Use `bsn!`/`Template` for typed construction of session shape, producing ordinary `Node` trees: `workspace("default") [ root("main") { Node { flex_direction: Row } [ pane(shell()) { Node { flex_grow: 1.0 } }, pane(argv, cwd) { Node { flex_grow: 1.0, min_width: px(20.0) } } ] } ]`. Templates produce inert intent entities (`PaneTemplate { argv, cwd, env, size }`) that the `Requests` phase materializes through the same validated transitions as a client request; they never spawn processes themselves. Uses: the default startup session, `zor run` ephemeral workspaces, restore templates, the viewer's own chrome and popups, zor's dashboard scenes, tests. `.bsn` files are not shipped by Bevy 0.19.1; ship user layouts and templates as `ScenePatch` assets through a fux `AssetLoader` (the community-loader path Bevy documents at `bevy_scene/src/lib.rs:881-883`, modelled on `benches/benches/bevy_scene/spawn.rs:405-417`) so they hot-reload like every other asset.

Everything user-editable is a `bevy_asset` `Asset` with a fux `AssetLoader` and `file_watcher`: configuration, themes, keybindings, session templates, user layouts. Systems react through `AssetChanged<T>` queries and `AssetEvent`s; viewers hold `Handle<Theme>`. Reloading configuration never restarts panes; a reload that fails validation keeps the previous asset and logs why. The user-facing configuration keeps today's vocabulary so existing files keep meaning: `prefix`, `default-command`, `clipboard`, `[bindings]`, `[history].scrollback-lines`, `[limits]`, `[final].retain-ms`, `[style]` (the sixteen ANSI names, `default`, `none`). `[style]` loads into a `Theme` asset of named tokens (`bar`, `bar-background`, `tab-active`, `separator`, `separator-focused`, `notice`, plus pane-border and focus-ring tokens) resolved by a system in the `bevy_feathers` manner — `ThemeToken` names on chrome entities, one resolve pass per theme change — instead of colours stored on every entity.

### 3.8 Persistence and restart restoration

Persist the session as a scene, never the live World: for each workspace the allowlisted layout subgraph of 3.4 plus `LaunchAttribution`, `Name`, focus, cwd and an optional bounded screen history marked historical. Implementation: an extraction system copies allowlisted reflected components into a snapshot World; `DynamicWorldBuilder::deny_all()` with explicit allows; serialize RON; write atomically (temp file + rename) under `$XDG_STATE_HOME/fux/session/`. Restoration loads into an inert World, validates references and limits, allocates fresh entities, links relations, then materializes processes through the template path with explicit per-pane restore/skip decisions exposed over BRP. Never serialize sockets, PTY descriptors, handles, viewer authority or attachment state. `bevy_world_serialization` reload paths despawn and respawn instances; do not use asset hot reload against the live World. A saved session and an exported layout are the same document type; the only difference is whether `PaneTemplate`s are honoured.

### 3.9 Control protocol: BRP over `RemoteHttpPlugin`

Transport: `RemotePlugin` + `RemoteHttpPlugin` from `bevy_remote`, bound to `127.0.0.1`. `RemoteHttpPlugin` never reads back the bound port, so fux pre-probes a free port (`TcpListener::bind("127.0.0.1:0")`, read `local_addr`, drop), passes it with `with_port`, and overwrites the public `HostPort` resource so `rpc.discover` agrees; the TOCTOU race is accepted and a bind failure retries with a new probe. The port and a fresh 256-bit capability token are written 0600 to `$XDG_RUNTIME_DIR/fux/<server>.brp.json`. No other listener exists besides the attachment stream (3.10).

What `RemoteHttpPlugin` does and does not give (`bevy_remote/src/http.rs`): it accepts any connection, buffers the whole body unbounded, dispatches batches of any size, spawns one task per connection without a cap, applies no request deadline (hyper's `.timer()` only serves header-read timeouts), and hands handlers `BrpMessage { method, params, sender }` — **no headers, no body, no peer**. Consequently:

- Authority is the token, enforced inside every registered method: each handler is fux's own system that rejects requests whose `params.token` does not match (constant-time compare) before doing anything. The built-in reads (`world.query`, `world.get_components`, `world.get_resources`, `world.list_components`, `world.list_resources`, `world.get_components+watch`, `world.list_components+watch`, `registry.schema`, `rpc.discover`, `schedule.list`, `schedule.graph`) are registered under their standard names as token-checking wrappers that delegate to the public `bevy_remote::builtin_methods::process_remote_*_request` systems: the instant ones by direct call `(In(params), world)`, the two `+watch` ones through `world.run_system_cached_with` because their `Local` state has no public constructor. Method names follow `bevy_remote::builtin_methods::BRP_*_METHOD` constants at the pinned version.
- Never registered: `world.spawn_entity`, `world.insert_components`, `world.remove_components`, `world.despawn_entity`, `world.reparent_entities`, `world.mutate_components`, `world.insert_resources`, `world.remove_resources`, `world.mutate_resources`, `world.trigger_event`, `world.write_message`. Because `RemoteMethods` has no `remove`, fux's plugin runs after `RemotePlugin` and replaces the resource with a fresh table containing only the allowlist. A test asserts `RemoteMethods::methods()` equals the allowlist as a set, and that authoritative components are absent from the type registry (`reflect_auto_register` is off), so even a bug in the allowlist cannot reach them.
- `world.observe+watch` is registered as a token-checked wrapper that validates `params.event` against the allowlist of public lifecycle events (section 3.3; each derives `Reflect` with `#[reflect(Event)]` and is `register_type`d) and refuses any other type path. The built-in buffer is unbounded and its observers are never despawned, so the wrapper owns a bounded per-stream buffer and despawns its observer when the stream closes.
- Watch rules from the transport: streaming is selected by the literal substring `+watch` in the method name and is refused inside batches; a stream's `params` are re-run every tick and cannot change mid-stream, so cursor resume is a new request. An unknown method name makes the dispatcher `return` for that tick, delaying later queued messages; the allowlist wrapper answers unknown names itself so this cannot happen.
- Not mitigated by this design and recorded in `docs/security.md`: body/batch/connection bounds and request deadlines cannot be enforced from a handler. Loopback plus the token limits *who* can spend those resources, not *how much*. If the resource-exhaustion scenarios in section 5 fail, the fallback is a fux hyper service feeding the same `BrpSender` mailbox with limits, upstreamed to Bevy as a `RemoteHttpPlugin` option; `RemoteHttpPlugin` is not forked in-tree.
- Response headers set no CORS allowances (`with_headers` is never used). A browser "simple request" can reach the listener but cannot present the token; DNS rebinding likewise. Any process that can read the 0600 token file has full authority, exactly as a process that could connect to the old 0600 socket did; kernel peer credentials are gone, so per-connection identity is the token, not a UID. `docs/security.md` must say this in the first paragraph.

Method table namespaces:

- `fux/*` typed commands: `workspace.{list,new,kill,rename,order}`, `root.{new,close,rename,order,move}` (a root is what the viewer shows as a tab), `node.{spawn,despawn,reparent,reorder,patch}` (template edits, the scene-edit primitives of 3.4; `patch` takes reflected field paths into `Node`/`ZIndex`/`BackgroundColor`/`BorderColor` and is the only reflected mutation fux exposes, validated field by field), `viewer.{list,show,target,scroll,zoom,unzoom}` (instance-side, addressed by viewer; `target` is the old `focus`), `pane.{new,close,send_keys,send_bytes,capture,final}`, `scene.{export,apply,list,save,restore}`, `surface.{open,update,close}` (3.13), `input.{reserve,submit,status}`, `server.info`, `token.{mint,revoke}`, `schema`.
- The wrapped `world.*` reads and `registry.schema` (read-only) over reflected projection components only (`PaneView`, `NodeView`, `RootView`, `WorkspaceView`, `ViewerView`, `ServerView`) keyed by public ids. `rpc.discover` advertises exactly the allowlist but carries names and the server URL only (its `MethodObject`s have empty params); per-method param/result schemas are fux's own `fux/schema` method and fixtures, not `rpc.discover`.
- `fux/events+watch { cursor }` backed by the retained per-workspace event log with explicit gaps and server incarnation; BRP's tick-driven watch is only a delivery loop, so the handler resumes from the client's cursor and reports `gap` rather than dropping the connection. Watch responses are delivered as `text/event-stream` by `RemoteHttpPlugin`.

Every mutating method carries the server instance nonce and, where applicable, `LayoutGeneration`; stale or conflicting requests are rejected, never misapplied. Workspace scoping is a method parameter validated against the token's grants, replacing today's per-workspace sockets: `fux/token.mint { workspace, capabilities }` (server token required) returns a narrower token, `fux/token.revoke` invalidates it immediately including its open watches, and the token table is a bounded resource that is never persisted. Frequent lifecycle events are paced: `PaneOutput { seq }` is triggered at most once per `OutputPacing` interval per pane, carrying the latest sequence, exactly as today's `pane.output` event.

### 3.10 Attachment stream

A second listener is unavoidable for the viewer stream because BRP/HTTP request-reply and SSE cannot carry bidirectional input at terminal latency. Keep it Bevy-native: a `TcpListener` on loopback accepted on `IoTaskPool` (`async-io`), random port and token published in the same `brp.json`, `Hello { token, instance, workspace, stream, viewport, exact_target? }` as the first frame, then length-prefixed frames. **The frame is the viewer's instance scene**: `Scene { revision, delta: DynamicWorld }` carries the changed allowlisted components of this viewer's instance roots (`Node`, `ComputedNode`, `ZIndex`, `BackgroundColor`, `BorderColor`, `Name`, `PaneId`, `NodeId`, `Zoomed`, `RootOrder`, the `Targets` pane, plus the surface subtrees of 3.13) with server-stable `NodeId`s for entity mapping, and `Cells { pane, seq, rows delta }` carries terminal content in a binary row format; `Input`, `Mouse`, `Resize`, `View`, `Control(JSON-RPC request)`, `Reply`, `Detach`, `Exit { code }` are unchanged in role. Because each viewer has its own instances, a frame never carries another viewer's geometry and no per-viewer filtering of a shared tree exists. The viewer applies scene deltas into its own World with `write_to_world_with` and an `NodeId → Entity` map, so its chrome and the server's layout live in one `bevy_ui` tree. Deltas derive from `ProjectionBaseline` per viewer (extraction pattern, no shared render world). Exact-process attachment (pin instance/stream/pane/pid, close on route or identity loss) is preserved. koh forwards a byte stream today over a Unix socket; forwarding a loopback TCP stream is a koh change that must go upstream first, and until it is published the multi-machine composition gate is *unavailable*, not passed.

### 3.11 Viewer

The viewer is a real Bevy `App` with the same stack minus PTYs. Its World holds the replicated instance scene (3.10) plus viewer-local `bevy_ui` trees for chrome: the bar and tab strip (a projection of `RootOrder`/`Name`), the command column, choosers, prompts, confirmations, notices, copy-mode overlays. **Presentation focus lives here and only here.** Because the viewer has exactly one focus and one terminal, `bevy_input_focus` is used unmodified: the viewer spawns one `Window` entity marked `PrimaryWindow` (`WindowResolution::new(cols, rows).with_scale_factor_override(1.0)`; inert without winit, resized on `SIGWINCH`, which the runner receives on its signal channel); terminal input is parsed once into `bevy_input` messages (`KeyboardInput`, `MouseButtonInput`, `MouseMotion`, `MouseWheel`) plus `bevy_window::Ime::Commit` for bracketed paste; `ButtonInput<KeyCode>` answers chords; `InputFocus` names the focused replicated pane and `InputDispatchPlugin` (feature `keyboard`) delivers `FocusedInput<KeyboardInput>` bubbling from the pane up through the replicated tree to command-mode handlers; the viewer registers `dispatch_focused_input::<Ime>` itself because the plugin only dispatches `KeyboardInput` under the chosen features. A `FocusGained` on a replicated pane sends `viewer.target` to the server (so the server's `Targets` follows the viewer's focus, never the reverse) and the pane's bytes are then sent on the attachment stream. Replicated panes carry `TabIndex` in projected order under one `TabGroup`, so `TabNavigationPlugin` gives pane cycling; a viewer system rebuilds a `DirectionalNavigationMap` with `auto_generate_navigation_edges` from `UiGlobalTransform` centres after every scene delta, so `h j k l` are `DirectionalNavigation::navigate(CompassOctant)` calls that work on any layout, not just splits; click-to-focus triggers `AcquireFocus` from the `Pointer<Press>` observer because `click_to_focus` is feature-gated off; focus changes are consumed through `FocusGained`/`FocusLost` (delivered after `PostUpdate`), never by polling `InputFocus`; focus history for "return to previous pane" is a viewer-local ring of `NodeId`s. Keybindings are a `HashMap<KeyChord, SystemId>` of one-shot systems (`world.register_system`) loaded from the keybinding asset, so config and plugins bind keys to systems by name. Chrome is built from the `bevy_ui_widgets` idioms (`ListBox`/`ListItem` with a roving `ActiveDescendant` for the tab and workspace choosers and the command column; `MenuPopup` dismissal-on-focus-loss for the corner box; `ScrollArea` for copy-mode history; the `text_input` key-to-edit queue reimplemented over a plain `String` for rename/new-workspace prompts, since `bevy_text` is unused); widget outputs are `Activate` and `ValueChange<T> { is_final }` events, and only `is_final` values produce BRP mutations. Modes are `bevy_state` `States`/`SubStates` with `ComputedStates` for "a modal is open"; notice TTLs are `Timer`s. Painting is one pass over the viewer's own `UiStack`: for every `ComputedNode` in stacking order draw `BackgroundColor`, `BorderColor` border cells, then the node's content (terminal grid for panes, text for chrome and surfaces) into a cell buffer, and diff it to `termina`; no ratatui. Copy mode, selection and private history remain viewer-local components.

Optional maximal variant, to be decided by measurement in milestone 2, not by default: each attached viewer as a `bevy_app::SubApp` with its own World (its instances, camera, picking pointer, states), with an exclusive extract system copying `Terminal` deltas in and `Targets`/input messages out — the render-world pattern without `bevy_render`. Adopt it only if per-viewer isolation measurably simplifies the instance/target code; otherwise instances in the main World are sufficient.

### 3.12 Command line

`fux` (attach or create `default`), `fux NAME`, `fux serve --name`, `fux attach --brp FILE [--pane ID --pid PID]`, `fux workspace list|new|kill`, `fux bindings`, `fux [NAME] layout save|load NAME`, and `fux [NAME] <method> [json]` as a thin BRP client that reads `brp.json`, adds the token and prints the reply; `fux [NAME] events --cursor N` streams SSE. `split`, `swap` and `close` exist here as convenience compositions of `node.*` calls. `zor run -- CMD` keeps its contract (ephemeral workspace, final evidence, exit status). The CLI shares the viewer's `bevy_input` parser and nothing else; it holds no World.

### 3.13 Surfaces: non-terminal content hosted by fux

A `Surface` is a leaf node whose subtree is not a terminal but a scene another app streams: zor's dashboard, a plugin's pane, a machine list, a diff view. `fux/surface.open { node, provider }` creates it; the provider sends `fux/surface.update { surface, revision, delta: DynamicWorld }` with an allowlisted vocabulary (`Node`, `Name`, `ZIndex`, `BackgroundColor`, `BorderColor`, `ScrollPosition`, and a `Text(String)` leaf component fux defines because `bevy_text` is unused); fux validates the delta against the same limits as a layout, applies it under the surface node, lays it out with everyone else and replicates it to viewers like any other subtree. Input to a surface is routed back to the provider as `FocusedInput`/`Pointer` events over `fux/events+watch` filtered to that surface, so a provider is a widget tree plus event handlers, exactly the `bevy_ui_widgets` shape, running in its own App. Bounds: nodes per surface, delta rate and bytes per second are per-token limits; a provider that exceeds them loses the surface. This replaces Herdr's "plugin panes are terminals" and gives zor a dashboard without a second TUI (4.5).

## 4. zor design

### 4.1 Model

A second `App` with its own World and the same runtime stack (`bevy_state` for task/attempt lifecycle, `bevy_time` for heartbeats and deadlines, `bevy_tasks` for provider subprocess I/O and Git, `bevy_asset` with `file_watcher` for rule bundles and plugin manifests, `bevy_log`): entities `Task`, `Attempt`, `Prompt`, `Operation`, `Check`, `Source`, `Artifact`, `Group`, `Worktree`, `Machine`, `Service`, `ObservedAgent`, `Plugin`, `PluginAction`. Relationships: `AttemptOf(task)`, `PromptOf(attempt)`, `CheckOn(source)`, `MemberOf(group)`, `Bound(machine)`, `OwnedWorktree(task)`. Provider adapters (Codex app-server, OpenCode plugin, Claude passive) and check runners are effect adapters in the `bevy_asset` server shape: work on `IoTaskPool`, results over a channel, one draining system per update emitting typed messages; the World never holds their handles. Lifecycle transitions that the current `zor-lifecycle-transitions.md` describes as a table become per-entity typed enum components with a single transition function per entity kind (`bevy_state` is app-wide and cannot model many tasks), while zor's own modes (`Idle`, `Supervising`, `Draining`) are `States`. The semantics that must survive verbatim from `crates/zor/TASKS.md`, `CHECKS.md` and `RESULTS.md`: durable operation ids with reservation → receipt → reconciliation, `uncertain` outcomes that are never auto-resolved, verification seals bound to one retained source, and refusal to replay on lost replies.

Durability: the journal becomes the persisted reflection snapshot of an allowlisted subgraph (same mechanism as 3.8) with the current bounds (4 MiB, task/attempt/prompt/group counts) enforced at extraction, atomic writes, and an archival lifecycle designed in rather than deferred: closed tasks past a configured age move, with their attempts/prompts/checks/artifacts, into dated read-only archive snapshots under `$XDG_STATE_HOME/zor/archive/`, the live snapshot keeps only open work plus a bounded tail of recent history, archived records answer `zor/task.inspect` read-only, and no archive step can drop an `uncertain` operation or an unresolved check. Receipts, uncertain states, verification seals and group semantics are re-derived from the zor markdown contracts and tested against the same scenarios. Rule bundles, plugin manifests and machine catalogs are `bevy_asset` assets with loaders and file watching; `Disabled` marks archived tasks so live queries never see them.

### 4.2 Talking to fux

zor is a BRP client of fux over loopback HTTP, reading fux's `brp.json` for port and token: typed `fux/*` calls, `world.query` over projections for observation, `fux/events+watch` (SSE) with cursors for lifecycle. The service-ownership rules stay: zor validates instance/stream/pane/pid before destructive operations; transport reconnection never authorizes replay.

### 4.3 BRP surface of zor

`zor/*` methods (task/prompt/check/source/artifact/group/worktree/machine/plugin operations), the same token-wrapped read-only `world.*` set over `TaskView`, `AgentView`, `MachineView`, `CheckView`, and `zor/events+watch`. Same allowlist discipline and test as fux.

### 4.4 Plugin host (replaces Herdr's plugin daemon)

zor owns the host surface Herdr describes: manifest (`zor-plugin.toml`: actions, event hooks, panes, link handlers, keybindings, platforms, build/startup commands), install/link/enable, logs, invocation context. Plugins are ordinary processes started with `FUX_BRP` and `ZOR_BRP` (paths to the respective `brp.json`) and `ZOR_PLUGIN_*` context env, and call back over BRP; `registry.schema` plus `fux/schema`/`zor/schema` are their type documentation. A plugin pane is either a terminal pane (`fux/node.spawn` with a `PaneTemplate`) or a surface (3.13) the plugin drives with scene deltas; placements (`overlay`, `split`, `tab`, `zoomed`, `popup`) are templates over `node.*`/`root.*`. Event hooks consume `fux/events+watch` and `zor/events+watch` with cursors. No restricted SDK: the BRP method table plus the surface vocabulary is the plugin API.

### 4.5 Supervision, machines, dashboard

Re-implement the current saved-machine catalog, per-machine observation workers, exact-pane handoff, guarded remote actions and resume intents over the new model; koh helper ownership unchanged. The dashboard is not a separate TUI: zor builds it as a `bevy_ui` scene from its projection components (`bsn!` templates over `TaskView`/`AgentView`/`MachineView` rows, `ListBox` idioms) and streams it into a fux surface (3.13); actions on rows arrive back as surface events and become `zor/*` calls. `zor dashboard` therefore means "open a workspace with a dashboard surface", and the same scene is what a remote machine's zor streams through koh.

## 5. Verification

- Property tests over random template-edit sequences (spawn/despawn/reparent/reorder/patch on arbitrary flex, grid and absolute trees) interleaved with viewer attach/detach/show/resize/zoom, asserting section 3.5 invariants, pane/PTY identity and that every instance equals its template in shape after each update; run against the real `bevy_ui` layout systems, not a mock.
- Layout mechanism test first: a root under a `UiTargetCamera` whose `target_info` is 80×24 yields an 80×24 `ComputedNode` with no window and no renderer; then a matrix of flex/grid/absolute/overflow layouts at several viewports with expected cell rects. Old `layout.rs` fixtures are used only to check that the default split templates produce the same rects users see today for plain two- and three-pane splits; no other compatibility is owed to the split tree.
- Fixture round-trips for every BRP method's params/result schemas and every attachment message (`deny_unknown_fields`); the fixtures are what zor, plugins and koh consume. `rpc.discover` output is itself a fixture.
- Real-process scenarios with disposable XDG directories: spawn/exit/retire, receipts, exact attachment loss, layout apply with stale generation, session save/restore with skip/retry, event watch resync after gap, config asset hot reload with an invalid edit.
- Picking backend tests: cell → entity hits and border regions on nested flex/grid/absolute layouts, zoomed instances and two viewers with different viewports showing the same root (each hit resolves to that viewer's instance); a test that no system reads `Hovered`/`DirectlyHovered`.
- Viewer tests against a pseudo-terminal: tab and `h j k l` navigation reach every pane in projected order; a panic inside a system restores the outer terminal; `SIGWINCH` re-lays out within one update; a chooser dismisses on focus loss.
- Shutdown tests: `SIGTERM` with live panes terminates every process group within the deadline and exits with the documented status; a hot pane streaming output does not delay signal handling beyond one step.
- BRP: allowlist test; authoritative components absent from the type registry; a request without the token or with a wrong token reaches no handler side effect; resource-exhaustion scenarios (oversized body, 10,000-element batch, 1,000 idle connections, a stalled body) recorded with their observed effect on the server — failures here trigger the fallback in 3.9, not a silent pass.

## 7. Delivery rules

**This is one continuous session.** Execute milestones 1 through 8 in order without stopping between them, without asking for confirmation, and without treating elapsed time, token or tool budgets, or the size of the remaining work as a reason to yield. A milestone boundary is a commit, not a hand-off. The only legitimate stops are: an external prerequisite that no tool in the session can obtain (a network fetch that fails repeatedly, a platform that is not present), or a contradiction between this document and Bevy source that cannot be resolved by the precedence rule in section 1. In either case record the exact blocker in `docs/verification.md`, finish every milestone task that does not depend on it, and only then report.

Authorized in advance for this session: creating the `ecs-rewrite` orphan branch and worktree, committing on it at every milestone and at any point where a revert target is useful, creating the `../fux-rewrite` directory, fetching crates from crates.io, and cloning read-only references into `references/`. Not authorized: pushing, tagging, publishing, opening PRs, modifying `main` or `references/`, touching the user's running fux/zor sessions, or spending resources outside this machine.

Session discipline: keep `docs/HANDOFF.md` in the worktree current after every commit (milestone reached, next task, open blockers, exact commands to resume), so that if the session is interrupted for reasons outside its control a new session resumes from the last commit without re-deriving state. Run the milestone's own tests before its commit; run the full suite, formatter and lints at milestones 2, 5 and 8. Prefer finishing a milestone over polishing an earlier one; go back only for a failing test, a violated invariant, or the review pass below.

**ECS-native review after every milestone.** Before the milestone commit, read every file written or changed during the milestone as a reviewer, not as its author, with `docs/bevy-source-patterns.md` open beside it, and for each ask whether Bevy already provides the mechanism that code hand-rolls; the patterns document names, per Bevy file, the mechanism and its caveats, so a review finding cites the pattern section it applies. The checklist, with the replacement in each case: a `bool`/`Option` field that encodes presence → a marker component or `Disabled`; a `Vec<Entity>`/`HashMap<_, Entity>` field that mirrors a parent, owner or membership → a relationship pair; a struct that several system sets write → split by mutation owner; a `dirty` flag or manual revision used only inside the World → `Changed<T>` with `set_if_neq`; a match on a mode enum inside many systems → `bevy_state` `States` with `in_state` run conditions, or a per-entity enum with one transition function; a callback, channel or `Box<dyn Fn>` reacting to a World change → an `EntityEvent` and an observer, or a hook if it is pure index maintenance; a hand-written traversal of `Children` for a bubbling reaction → `#[entity_event(propagate)]`; geometry, hit-testing, focus traversal or navigation arithmetic → `bevy_ui`, `bevy_picking`, `bevy_input_focus`; a hand-written loader, watcher or reload path → `bevy_asset`; a timer or elapsed-time field → `bevy_time`; a counter or gauge → `bevy_diagnostic`; a bespoke serialization of entities → reflection over an allowlisted `DynamicWorld`; a `&mut World` system that exists only because components were coarse → typed queries once they are split; an allocation on the hot path → a reused buffer. Where a more ECS-native form exists, rewrite it in this milestone unless the rewrite would cross into a later milestone's scope, in which case record it in `HANDOFF.md` under "ECS-native debts" with the file, the mechanism to use, the patterns section and the milestone that will take it, and clear that list before milestone 8's commit. When the review discovers a Bevy mechanism or caveat the patterns document does not cover, add it there with a citation, so the document grows with the code. Record each pass in `docs/verification.md` as "ECS review: N files, M rewrites, K debts". A milestone with a review pass that found nothing is suspicious; look again at the largest file it added.

Work only in the `ecs-rewrite` worktree. Use isolated runtime directories, ports and tokens in tests.
