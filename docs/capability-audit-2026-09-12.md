# Herdr versus fux + zor + koh: capability audit, 2026-09-12

The stack is a credible foundation for controlled headless agent workflows, with explicit delivery, correlation and verification contracts beyond Herdr's documented terminal/agent orchestration API. Its verification path is currently limited to very small committed source trees: it cannot retain the current fux repository as a source snapshot. It is not yet a complete Herdr replacement. Herdr leads substantially in integrated multi-machine use, agent breadth, restart restoration, terminal/workspace interaction, extensibility and native Windows distribution. No current evidence establishes universal performance or reliability superiority.

**Scope and evidence.** Compared fux main `1792223` (fux 0.10.0, zor 0.5.0, local-ipc 0.2.0), its pinned koh `f6a3352`, and Herdr master `d184b41` (latest stable release 0.9.0). Koh main `c486531` is six commits ahead of the pin; its net change is CI configuration. Herdr's current master includes post-0.9.0 work, notably saved-machine CLI routing; the core multi-machine UI already appears in the release documentation. Inspected current source, public method inventories, shipped documentation, capability command output and retained verification. This is a capability and implementation audit, not a fresh end-to-end benchmark or exhaustive runtime certification of Herdr. Third-party Herdr plugins are outside the comparison; their existence means missing core workflows can sometimes be supplied externally.

## Reading the evidence

This document separates four kinds of evidence: **implementation** (inspected source/API), **recorded tests** (fixtures, owned processes and prior verification), **real-provider acceptance** (actual provider behavior under a stated scenario), and **comparative acceptance** (the same workflow exercised in both products). Source and test coverage do not substitute for the latter two. “No equivalent found” refers to inspected core surfaces; it does not prove impossibility through scripts or plugins. Version-specific findings apply to the pinned commits above, not automatically to their latest stable packages.

Particular attention is given to source/check capacity, provider recovery, Windows remote support and CI provenance. The source-size inventory is a read-only measurement of committed Git objects; no new provider, WAN or performance experiment was run.

## The stack's strongest existing advantages

Herdr's `agent prompt --wait` is more careful than simply sending keys and looking for idle: it pins the occupant, refuses an already-blocked agent, orders submission, and requires observed activity for a prompt sent from a settled state. However, its documented wait does not identify a particular turn; an already-working turn can satisfy it. A timeout does not establish whether input was sent. Zor's retained operation and receipt machinery makes those uncertainty states explicit and supports reconciliation under the original identity and deadline. Native Codex and managed OpenCode add correlation to the provider's particular input/turn. These guarantees remain bounded by retention and provider behavior; they do not establish exactly-once semantic execution of arbitrary agent work. [Herdr automation](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/docs/next/website/src/content/docs/agent-automation.mdx), [zor task contract](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/TASKS.md), [implemented adapter contract](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/src/tasks/capabilities.rs).

Input safety has multiple axes. Generic zor task submission revalidates the pane root PID, but that does not establish which foreground program will consume the input. Herdr's occupant-aware wait and zor's durable delivery identity therefore address different failure modes. Receipt deduplication is not a reason to drop foreground validation or assume exclusive ownership of a terminal. [Target identity contract](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/TASKS.md).

Fux also exposes retained, sequenced event replay with explicit gaps. Herdr's documented lifecycle subscription starts at acceptance and does not replay earlier events; its cache-bootstrap recipe subscribes, snapshots, then applies buffered events. Both have usable synchronization approaches, but retained replay is an additional fux primitive. [Herdr event API](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/docs/next/website/src/content/docs/socket-api.mdx), [fux event log](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/fux/src/ecs/events.rs).

Zor's result seal requires the latest passing required checks on one retained source, with the required artifacts captured by those checks. Its groups can gate later prompts on that verification. This is a substantial built-in workflow capability beyond Herdr's core terminal/state API. The seal proves the declared checks and retained bytes, not semantic code correctness or sandbox isolation. Likewise, a group advances already-prepared prompts; it does not invent a plan, launch all workers, verify their results automatically, merge branches or repair failed work. [Verification](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/RESULTS.md), [groups](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/GROUPS.md), [scheduler implementation](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/src/service_tasks.rs), [handoffs](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/HANDOFFS.md).

## Verification is implemented, but not yet practical for representative repositories

`source-collect` reads the **entire committed Git tree** of a managed task's owned, ready worktree. It does not collect a patch or select a small subtree. Dirty, untracked and ignored files are excluded. Supported inputs are regular files; symlinks, submodules and several path forms are rejected. Git LFS pointers remain pointer bytes. These restrictions materially narrow the “verified task results” advantage. [Source contract](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/SOURCES.md), [collection and validation](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/src/tasks/source.rs).

A read-only inventory at fux `1792223` gives:

|---|---:|---:|---|
| Whole repository | 471 | 6,911,050 | No: exceeds 256 files and 262,144 bytes; 14 files also exceed the per-file bound |
| `crates/fux/` | 90 | 1,069,669 | No: exceeds total bytes; shown only as a size diagnostic |
| `crates/zor/` | 169 | 2,380,455 | No: exceeds total bytes; shown only as a size diagnostic |

The per-crate rows are not supported collection modes. The current whole-tree path would reject this repository before publishing a source. Consequently, source-bound verification cannot currently verify a normal full fux checkout using that retained-input path. An unbound check can run in the live launch directory, but it cannot replace the common retained source required by the verification seal. This is an inference from measured inputs and enforced limits, not a recorded failing `source-collect` runtime experiment.

The inventory is reproducible without a checkout or running an agent:

```sh
git ls-tree -r -l --full-tree 1792223ea4a24905501823203b585e50906f0d38
```

Sum the size field for blob entries; count paths by prefix for the diagnostic rows. Gitlinks have no blob size and must be checked separately for unsupported submodules.

Even accepted snapshots bind only the initial supplied files. Source-bound checks run in new writable directories without `.git` metadata; they inherit programs/environment and may access the network or other files. They do not pin dependencies or provide isolation. Commands that require Git metadata need an explicit supported solution. A check's observed zero exit, successful artifact capture and task verification are separate outcomes; callers must inspect all required evidence. [Check execution](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/CHECKS.md), [verification selection](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/RESULTS.md).

### Operational limits and their consequences

These are ceilings, not promises that every ceiling can be reached simultaneously. Journal records and reservations share the serialized storage bound.

| Resource and scope | Current bound or behavior | Operational consequence |
|---|---|---|
| Source snapshot | 256 files; 64 KiB/file; 256 KiB file bytes; 32 KiB path bytes | Many ordinary repositories cannot enter source-bound verification |
| Sources per zor journal | 128 records; 512 KiB aggregate file bytes; no compaction | Even small successive revisions consume finite lifetime capacity |
| Checks per zor journal | 128 retained records; 64 KiB reserved per submitted result | Repeated verification eventually needs a supported history lifecycle |
| Check execution | CLI default 30 seconds; maximum five minutes; 256 KiB captured output per stream; 4,096 UTF-8 bytes retained per stream | Long builds and noisy commands exceed the runner contract; retained text is not a complete build log |
| Service check scheduling | Two active workers and four queued requests per service; CLI checks bypass those slots | This is not a global concurrency ceiling; overload must be handled |
| Service check reply | 15-second reply budget; a started check may continue afterward | Inspect the original execution ID; a missing reply does not authorize rerunning it |
| Check cancellation/cleanup | Task cancel/stop does not stop a submitted check; no check-cancel or automatic scratch-directory cleanup | Operator cancellation is incomplete; leader exit does not prove detached descendants stopped |
| Artifacts per zor journal | 64 KiB/file; 128 records; 512 KiB retained bytes; no compaction | Suitable for small reports, not general build products or long logs |
| Check/artifact eligibility | Managed tasks only; source collection additionally requires an owned ready worktree | Adopting an arbitrary existing terminal does not grant the full verification workflow |
| fux input receipts | 128 globally per server, at most ten minutes; unexpired receipts are not evicted to admit input | Capacity applies backpressure; the caller must reconcile within the retention window |
| fux final records | 128 globally per server, at most four hours; capacity can evict earlier | Four hours is a maximum requested lifetime, not a guaranteed observation window |
| fux event replay | Per workspace: 1,024 events or 512 KiB, whichever fills first; volatile | Consumers must handle replay gaps and server incarnation changes |

Source/check/artifact values come from [SOURCES.md](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/SOURCES.md), [CHECKS.md](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/CHECKS.md) and [ARTIFACTS.md](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/ARTIFACTS.md); fux values come from [resources](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/fux/src/ecs/resources.rs), [retention protocol](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/fux/src/proto/control.rs) and [event log](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/fux/src/ecs/events.rs). Retained zor records survive separately from fux's volatile evidence; journal durability does not extend a receipt or replay window.

## Recovery and longevity remain unfinished

Fux persistence currently means keeping its server and pane processes alive across viewer detach. It does not restore the workspace after server/machine restart. Durable zor records remain useful, but records alone do not recreate a terminal or recover all agent workers. OpenCode recreation can explicitly target a replacement fux incarnation when the old attempt is lost; it still requires a prepared destination workspace and the eligibility conditions above. Herdr already restores session shape and launches supported agent resume commands; arbitrary old processes do not survive a restart there either. Its live PTY handoff is a separate, experimental operation. [fux persistence](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/README.md), [zor recreation](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/src/tasks/resume.rs), [Herdr restore implementation](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/src/persist/restore.rs), [Herdr native resume implementation](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/src/agent_resume.rs).

Specific stack limits relevant to a long-running service:

- Zor's journal is bounded to 4 MiB, with 128 tasks, 512 attempts and 1,024 prompts; groups are capped at 32. A limited `task forget` exists for tasks without managed launch history or delivered/uncertain prompts; it does not provide general managed-history compaction. These are retained-record limits, not evidence of support for unlimited repeated work over time.
- Abandoned checks can become `uncertain`. Current recovery does not resolve their effects or remove the resulting cleanup guard. This can continue to block owned-worktree removal.
- Group membership pins an attempt and currently prevents OpenCode recreation, including membership in retained groups. This is a meaningful gap in recovery of scheduled work, not merely a missing UI button.
- Generic `task prepare` accepts literal single-line prompts; it is not a general multiline/paste adapter. Native Codex is a separate input path.

## Remote reachability and integrated multi-machine operation

Koh supplies authenticated peer-to-peer gateways and a 30-second reconnect retention window. The stack has explicit separate viewer/control gateway identities. Local real-fux tests now demonstrate reconnect across five QUIC losses, rejection after actual retention expiry, fresh attachment to the surviving pane, and separation of viewer/control endpoint grants. The fux gateway path does not inherit standalone koh's predictive local echo. Those tests run on one machine and do not establish WAN relay/NAT/mobile suspend behavior. Access separation also is not an OS sandbox: a viewer with a shell can exercise that account's normal local privileges. [Gateway implementation](https://github.com/gold-silver-copper/koh/blob/f6a335237c25aefde9b93290b19a8d909598a95d/src/gateway/sessions.rs), [composition contract](https://github.com/gold-silver-copper/fux/blob/1792223ea4a24905501823203b585e50906f0d38/crates/zor/REMOTE.md), [gateway tests](https://github.com/gold-silver-copper/koh/blob/f6a335237c25aefde9b93290b19a8d909598a95d/tests/gateway.rs).

Herdr supplies saved SSH machines, remote setup, a combined machine/workspace/agent UI, background metadata updates, independent reconnects and machine-scoped navigation. Current master additionally supplies `--machine` automation routing. Herdr's documentation disagrees on Windows scope: the connecting-machines page still restricts it, but the Windows support page advertises standalone remote attach and saved SSH machines to Linux/macOS/Windows hosts. Current remote preparation code also supports Windows targets and checks for saved-endpoint federation support. Windows hosts require a compatible preinstalled package on `PATH`; remote attach does not install/update it. This audit did not exercise Windows clients or hosts. The stack lacks that integrated product layer. For literal Herdr replacement, peer-to-peer transport alone does not replace it. [Herdr machines](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/docs/next/website/src/content/docs/connecting-machines.mdx), [machine CLI implementation](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/src/cli/machine.rs).

Windows evidence: [platform support](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/docs/next/website/src/content/docs/windows-beta.mdx), [Windows remote preparation](https://github.com/herdrdev/herdr/blob/d184b41fa36923c132629af725ff98bb02aa1b61/src/remote/attach.rs). Direct terminal attachment and live handoff remain unsupported on Windows; desktop support does not imply every Unix feature is portable.

## Human control and transcript retrieval

Herdr offers a separate writable per-terminal session with one controller and explicit takeover, alongside read-only ANSI observers without input, resize, scroll or takeover authority. fux's workspace attach, capture and event subscription do not establish equivalent per-terminal ownership semantics. This is a separate parity target from prompt receipts.

Herdr's alternate-screen transcript reads are conditional: they actively scroll only recognized idle agents at the transcript bottom with suitable mouse reporting. Working/blocked/unknown agents can reject explicit large reads with `agent_not_idle`; passive reads are a separate path. This is still a capability beyond host scrollback capture, but not unrestricted transcript extraction. ## How close are we?

For Unix terminal multiplexing plus carefully controlled Codex/OpenCode workflows, the important foundation exists. A user who values receipts, retained checks/artifacts and explicit verification may already prefer the stack. For broad everyday agent supervision, Herdr still covers many workflows the stack cannot currently provide. For a strict whole-product superset, this is substantial remaining work across several subsystems. A single percentage would conceal the difference between implemented primitives, real-provider acceptance, and missing product features. No defensible calendar estimate follows from this audit alone.

## Recommended order and acceptance gates

1. **Make verification usable on representative repositories.** Support committed input sizes and file forms needed by real target projects, address Git-metadata-dependent checks, and provide suitable check time/output and artifact storage policies. Keep explicit rejection and source binding. Exit: the full fux repository plus representative external projects complete source collection, required checks, artifact capture and verification, including negative tests for stale/mixed-source evidence. Merely increasing one constant is insufficient because aggregate journal/reservation bounds also apply.
2. **Finish the supported-agent vertical slices.** Run actual Codex, Claude and OpenCode tasks through launch, multiline prompt, response correlation, permission/question interaction, interruption, lost reply, process death and native resume. Implement the missing Claude adapter and clear limitations in the others. Exit: each advertised flow has recorded real-provider acceptance, not only scripted fixtures.
3. **Make repeated unattended operation sustainable.** Add explicit resolution for uncertain checks/launches, journal archival/compaction, grouped-task replacement/recreation, and restart recovery without duplicate input. Exit: a multi-day run survives controller/worker/server restarts and exceeds current retained-history limits without manual journal replacement or ambiguous cleanup.
4. **Build an integrated operator experience over the separate programs.** One entry point, sensible launch templates, an agent attention view that navigates to the right host/workspace/pane, deliberate blocker response, integrated worktree use. Exit: the usual Herdr supervise/respond/review loop needs no socket-path or incarnation bookkeeping.
5. **Close restart and remote-workspace parity.** Persist generic session shape, connect it to agent-specific resume policies, add saved machine profiles, scoped routing, independent reconnect and cached-state handling. Validate actual WAN loss/NAT/relay/mobile scenarios. Treat live PTY handoff as its own later acceptance target.
6. **Expand product breadth if literal superset remains the goal.** Broader provider integrations and versioned fixture coverage; pane move/swap/zoom and layout import/export; graphics and richer terminal interaction; plugin packaging/discovery; native Windows and installation/update paths. These are substantial features, not changes to a comparison table.
7. **Prove the final claim against matched releases.** Compare startup, idle and active CPU, memory, first-key/visible latency, sustained output, many panes/viewers, agent observation, remote loss, restart recovery and terminal correctness. Use equal workloads, build profiles, hardware and enabled features, retaining raw results. Repeat user acceptance across providers/platforms and a long soak.

## What would establish supersedence?

The following are proposed acceptance gates, **not passed tests**. A strict superset requires all applicable gates, including workflows where Herdr currently leads. The user may prioritize a narrower product, but that changes the claim.

| Scenario | Present evidence/status | Required proof |
|---|---|---|
| Full-repository verified change | Blocked for the current fux tree by enforced input bounds | Retain representative committed inputs, run real checks, seal matching artifacts, reject stale evidence |
| Native provider lifecycle | Uneven implementation; bounded fixtures/integration evidence; real-provider gaps above | Recorded launch, multiline input, correlation, blocker response, interrupt and resume for every advertised provider |
| Human intervention | Basic attach/focus; Herdr has richer terminal control/observation | Reliable takeover, read-only observation and return to automation without misdirected or duplicated input |
| Unattended operation | Finite journal history; unresolved check/group recovery | Multi-day soak with more than 1,000 task/check cycles, supported archival and injected controller/worker/server failure; no manual journal replacement |
| Session restart and live replacement | General fux restart restore/handoff absent | Restore layout/cwd/focus and supported agent state; separately demonstrate surviving PTYs during any advertised live handoff |
| Multiple hosts | Local gateway fault tests pass; integrated host UX absent | Two or more actual hosts, saved routing, combined attention view, independent reconnect, stale-state handling and WAN loss/relay tests |
| Provider/platform/terminal breadth | Large known gaps | Versioned provider matrix and platform runtime acceptance, layouts, transcript reads, graphics/input behavior and extension workflows |
| Comparative performance and reliability | No matched current-Herdr result | Publish reproducible paired workloads and raw measurements with equivalent enabled features and terminal-correctness checks |

For the performance gate, measure startup and steady-state CPU/memory across **all participating processes**, including zor and both koh gateway endpoints where used. Measure rendered input-to-visible latency (p50/p95/p99), not just command acceptance or a screen-hash proxy. Include warm/cold starts, multiple pane/viewer counts, sustained output and reconnect; pin builds, hardware, terminal and network conditions. Internal architectural benchmarks cannot establish this gate alone.

Implementation ownership should stay explicit: fux owns generic terminal/layout/persistence primitives; zor owns provider adapters, task policy, verification storage and recovery; koh owns authenticated transport/reconnect. A composed operator interface owns saved-machine discovery and cross-host navigation. This keeps the roadmap actionable without moving agent-specific policy into the terminal core.

The immediate priorities are representative-repository verification, real-provider acceptance, and grouped-worker/history recovery. The stack has distinctive orchestration contracts today; replacing Herdr in every way remains a substantial product and validation program.
